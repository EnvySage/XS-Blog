算法日记（一）：哈希表、链表与递归——把递归当黑盒用

学习周期：2026.08.30 ～ 2026.09.15（Day 0 ～ Day 15）
使用语言：Python 3
内容：从零开始刷 LeetCode 的过程记录——哈希表、链表、二叉树，以及第一次真正理解递归

一、Day 0｜Python 基础 + Two Sum 预习（2026-08-30）

今日内容

正式开启算法学习计划。今天没做题，先把 Python 和 Java 的差异搞清楚，为 Day 1 的 Two Sum 做准备。

学到的东西

1. Python 基本数据结构

  • 列表 [] ≈ Java 的 ArrayList，一个类型通吃
  • 字典 {} ≈ Java 的 HashMap
  • m.get(key, 默认值) 比 m[key] 安全，不会抛 KeyError

2. enumerate 是什么

  • for i, v in enumerate(nums)：enumerate 把索引和元素打包成一对，按顺序拆给两个变量
  • 不是什么魔法，就是省得自己写 nums[i]

3. 字典推导式

  • {v: i for i, v in enumerate(nums)}：本质就是 for 循环压缩成一行
  • 读法从中间往两边：{key: value for 变量 in 可迭代对象}
  • key 和 value 的顺序由自己决定，不是 enumerate 决定的

4. 字典 key 的选择

  • 你想查什么，就把什么放在 key 的位置
  • Two Sum 的需求是"给我一个值，告诉我它在哪"，所以值当 key、索引当 value
  • 索引当 key 几乎没用，因为数组 nums[i] 本身就是"索引 → 值"的映射

Two Sum 思路总结

踩坑记录

  1. 一开始加了 v == target 和 v < target 的判断——错误，题目要求的是两个数相加
  2. 只 append 了一个索引，忘了加上当前的 i——题目要返回两个索引
  3. 没有判断 m[sub] != i——可能配对到自己

二、Day 1｜哈希表三连（2026-08-31）

今日提交（一天完成）

题号 题目 状态 方法
#1 Two Sum ✅ 哈希表存"值 → 索引"，遍历查配对
#217 Contains Duplicate ✅ 边遍历边存 set，遇到重复返回 true
#242 Valid Anagram ✅ 字典计数，s 加 t 减，全归零就对

学到的东西

1. “先建再查” vs “边建边查”

  • Two Sum：先建完整字典，再遍历查 → 因为要排除自己，需要完整信息
  • Contains Duplicate：边遍历边建 → 因为碰到重复就要立刻返回

2. dict.get(key, 默认值)

  • 替代 if key in dict 的判断，一行搞定"没有就用默认值"

3. 字典 key 选择原则

  • 你要查什么，就把什么放 key
  • 数组本身就是"索引 → 值"，所以很少把索引当 key

4. 学习偏好确认

  • 不要语言特有的工具（如 Counter），只用跨语言通用写法
  • 不要直接给思路和答案，先让自己想

三、Day 12～14｜链表三题 + 第一次摸到递归（2026-09-07 ～ 09-09）

说明：这几天当时没有逐字记录，以下根据计划表笔记和进度记录回溯重建，细节从简；Day 15 起有完整对话可考。

这几天在学什么

从数组跨到链表，再跨到二叉树——正好是从"下标"到"指针"再到"递归"的三级跳。

踩坑与收获（回溯）

#141 环形链表——链表对象模型是第一道坎。 之前学数据结构都是在纸上画指针，真写代码才发现自己说不清：head 到底存的是什么？node = head 是引用不是复制——链表不像数组切片，赋值只是多了一个名字指向同一个节点。第一次接触链表必须先画图再上代码，脑内没有节点对象模型，写什么都是蒙。

快慢指针的结论：slow 走一步、fast 走两步，有环必相遇，没环 fast 先到 None。遍历链表的铁律是先判断再移动（while curr and curr.next），防止 None 越界。

#206 反转链表——三指针套路。 prev / curr / next_node：先把下一个节点存下来（不然一改指向就断链、找不回来了），再反转指向，最后整体前移。这题的"先存后改"是链表题的通用保命习惯。

#104 最大深度——递归的第一课。 当时还不会递归，用迭代写（while 一路往下走），写到"叶子走死了想回溯上一个节点"就卡住了——迭代回溯要自己维护栈，太麻烦。递归三行：空树返回 0，否则 1 + max(左, 右)。这个"迭代写不下去 → 递归降维打击"的体感，为 Day 15 的递归专题埋了伏笔。

四、Day 15｜递归专题：从"跟着链路走会绕晕"到"信任黑盒"（2026-09-14 ～ 09-15）

今日题目

#226 翻转二叉树 → #100 相同的树 → #101 对称二叉树 → #543 二叉树的直径。一天四题，全是递归，是计划里第一次正经碰"函数调用自己"这个东西。

思路演进

开局就撞上 Day 14 留下的墙。 我想给 #104 补一个迭代版（while 往下钻、height 计数），钻到叶子发现没有回头路，于是问："怎么回溯上一个节点？"答案是：迭代回溯得自己用栈存路径，而递归的调用栈就是那个栈，回溯是自动的。这句话后来成了理解递归的钥匙。

真正的坎在思维方式，当时的原话是：“跟着递归链路去思考的话会给自己绕蒙了。”

对，那就别跟。递归的正确打开方式不是模拟 CPU，而是三步框架：

  1. 这个函数做什么？——一句话定义，把参数和返回值说清楚
  2. 什么时候停？——不用递归就能直接回答的情况
  3. 当前层做什么？——假设子调用都会做对，我只处理我这一层

配套心法一句话：不要想"它怎么递归下去的"，只想"它返回后我怎么用结果"。 就像用 max(a, b) 不会去想 max 内部怎么比较——把递归函数当黑盒用。

#226 我写的第一版：

能跑，但"交换后 left 已经是原来的 right 了，我递归的到底是哪个？"——顺序一乱脑子就打结。改成先递归翻转左右子树，再交换，最后返回，逻辑上等价，人读起来就顺了。

教训：递归代码不仅要对，还要让自己不晕，顺序按"先问别人、再办自己的事"来摆。

#100 卡在停止条件：“不知道怎么思考停止条件”。判据是：停止条件 = 不用递归就能直接返回答案的情况。比较两棵树，“都是 None”、"一个是 None 一个不是"这两种当场能答，就是基准情形；"都不是 None"才需要往下问。顺带看懂了 return p.val == q.val and self.isSameTree(...) and self.isSameTree(...) 这种一行 and 链——拆成三个变量分别赋值更清楚，清楚优先。

#101 交出来的第一版栽在函数定义上：

isSymmetric(x) 的语义是"x 这棵树自己对称吗"，但镜像比较需要的是"两棵子树是否互为镜像"——函数签名里压根没有第二个参数可用。所以必须另开一个辅助函数 isMirror(left, right) 接收两个节点，主函数只负责调用它。

这天的骨架填空练习（if not left and not right: return ???）做完，当时的原话是"莫名其妙写出来蒙对了，我都没想明白"——其实每一行都有出处：三行守卫就是"自己能判断的"，最后一行 and 就是"外配外、里配里"，只是用 #100 的骨架改了配对方向而已。后来要求逐行讲解，拿这棵对称树：

走了一遍 isMirror(2,2) → (3,3) + (4,4) 的调用链才真正落地。

#543 直径是当天最绕的，但绕的方向变了。一开始质疑提示：“直径 = 左深 + 右深，那不是一般都会通过根节点？”——好质疑，反例是一棵歪树（根只有左链，最长路径 5→3→2→4→6 经过节点 2 根本不碰根），所以要遍历每个节点、拿它当转折点各试一遍，于是需要全局状态 self.maxDiameter 边走边更新。

代码上连撞三个 Python 的坑：

  1. 嵌套函数多写了 self 参数：def depth(self, node) 嵌在方法里再手动传就错位了——函数嵌在哪，参数就按谁算，嵌套函数不是方法，没有隐式 self。
  2. depth 定义在类缩进级别却被当方法调用，报 takes exactly 1 argument (2 given)——定义在类里就要 def depth(self, node) + self.depth(node) 成对出现，少一边都报错。顺带搞清了 self 指的不是 class，而是调用方法的那个实例对象（s = Solution() 里的 s），所以 self.maxDiameter 存的值在两次调用之间不会丢——这就是"全局状态维护"在 LeetCode 类模板里的写法。
  3. 质疑"记录直径和返回深度是不是功能重复"——不重复：maxDiameter = max(md, left + right) 是以我为转折点的完整路径（到为止，不往上传）；return 1 + max(left, right) 是我往下的单侧深度（必须往上传给爸爸用）。一个消费，一个供货。

写完发现这题"还能动态规划"——其实这个递归本身就是树形 DP：子问题的解（深度）被上一层复用。DP 和递归的关系也顺手理清了：递归是编程技术，DP 是"拆子问题 + 记住子问题的解"的思想，递归可以是 DP 的实现方式，但 #226 那种"翻完就走、结果不复用"的就不算 DP。

踩坑记录

  1. 迭代回溯难写：树/链的"回头"需要栈，递归的调用栈免费送，别硬写迭代。
  2. 先交换再递归（#226）：代码能过但人读晕，"先问别人再办自己"的顺序更防呆。
  3. 停止条件不会想：找"不用递归就能直接回答"的情况，就是它。
  4. 用 isSymmetric(左) + isSymmetric(右) 做镜像比较（#101）：函数签名对不上需求，双节点比较必须开辅助函数。
  5. 嵌套函数写 self、类方法漏 self：参数错位两连错，定义和调用必须成套。
  6. depth 忘记 return 1 + max(left, right)：递归函数没有返回值等于黑盒拒绝交货，上一层拿到的就是 None。

知识点笔记

  • 递归三步框架：一句话定义 → 停止条件（当场能答的）→ 当前层逻辑（信任黑盒）。全程不展开调用链，验证只拿两三个节点的小树手动 trace。
  • 辅助函数模式：一个签名解决不了两种语义时（自己对称 vs 两棵互镜），拆出去。
  • 全局状态维护：递归外挂号变量（self.xxx 或嵌套函数 + nonlocal），一边下探一边更新，"路径不过根"类问题的通用解。
  • 树形 DP 初体验：返回值往上传子问题解，顺便在局部消费组合答案，就是 DP 的雏形。

举一反三

  • #104 最大深度（Day 14）→ #543 直径（深度复用 + 全局状态）
  • #100 相同的树 → #101 对称（配对方向镜像）→ #572 子树（下一天的"找 + 验"双递归）
  • 迭代 vs 递归的选择：需要回溯优先递归；LeetCode 类模板里跨调用存数据用 self.xxx

一句话带走

三步框架：定义一句话，基准当场答，当前层只管"问完怎么用"——别当 CPU，当产品经理。

五、上篇小结

Day 0 ～ 15 走完了"数组 → 链表 → 树 → 递归"这条线，真正带走的其实只有四句话：

  • 想查什么，什么就放 key（哈希表）
  • 先存后改、先判断再移动（链表）
  • 定义一句话、基准当场答、信任黑盒（递归）
  • 只有值得跨调用维护的状态才挂 self（全局状态）

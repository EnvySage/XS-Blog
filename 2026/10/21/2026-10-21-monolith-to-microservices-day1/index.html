拆服务不是拆表：聊天室微服务化的第一步

学习日期：2026年10月21日
项目：Muchat-Back → muchat-cloud
环境：Java 21 / Spring Boot 3.3.5 / Spring Cloud 2023.0.5 / Spring Cloud Alibaba 2023.0.3.3

起因

Muchat-Back 是一个能跑的聊天室单体：用户、群聊、消息、通知、文件，全在一个进程、一个数据库里。

它没有坏。但所有东西都长在了一起：改一个通知模板要重新发布整个应用，消息表里掺着用户表的字段，一次本地事务横跨五个业务域。

我决定把它拆成微服务。第一天的目标不是"拆完"，而是先立四块地基：

  1. 基础设施能起来
  2. 工程骨架能编译、能测试
  3. 数据库边界先划清楚
  4. 所有流量有唯一入口

拆之前先留退路：原单体整体移进 legacy/，不参与 Maven 构建，随时能跑起来做对照。

微服务化的第一步不是拆代码，是保证你随时能回到拆之前。

一、先证明旧的还能跑

很多人一上来就新建模块。我先做的事是：让原来的单体在 Java 21 下完整构建，并调通验证码接口，确认返回 200 image/png。

这个动作看起来浪费时间，但它给整次重构定了一个基线：如果新架构出了问题，我能分清是"迁移引入的"还是"本来就有"。

基础设施同理。Nacos、MySQL、Redis、Kafka、Sentinel 用 Docker Compose 一次拉起，先确认每个组件都能连上，再写业务代码。

顺序是反的会怎样？你会同时怀疑三件事：代码写错了、配置写错了、中间件没起来。排查成本不是相加，是相乘。

二、拆服务的依据是业务域，不是表

最容易犯的错，是看着数据库表拆服务：users 一个服务，user_contacts 一个服务，chat_room 一个服务。

这样拆出来的不是微服务，是"分布式单体"的零件。

真正的判断依据是这几条：

  • 事务边界：哪些表经常在同一个本地事务里改
  • 数据归属：哪张表只有一个明确的写负责人
  • 访问模式：哪些数据总是一起查
  • 负载特征：哪些接口的 QPS 和延迟要求差一个数量级
  • 变更频率：哪些功能总是一起改
  • 团队边界：谁负责改、谁负责背锅

所以最后的划分是：

users 和 user_contacts 放一起，因为它们围绕同一个用户，经常一起查、一起改。

chat_room 和 chat_room_member 放一起，因为它们经常需要在同一个本地事务里修改：建群时同时写房间和成员，加人时同时更新成员和房间元数据。

message 单独拆出去，因为它的写模式和别的表完全不同：高频追加、几乎不更新、按 roomId 和时间范围查、需要独立的扩容策略，还需要一个专门的幂等键。

一句话：拆的是"谁负责写、谁负责改、谁负责扛量"，不是表。

三、拆库的本质是重新划分写负责人

表结构其实大部分可以原样保留。真正变的是规则。

原来一个库里有跨表外键，有触发器，有跨业务域的 JOIN。拆成四个 schema 之后：

  • 删除所有跨 schema 外键
  • 删除 trg_chat_room_member_set_room_name 触发器
  • 跨服务引用改成软引用，靠内部 API 校验
  • 跨服务查询改成 API 组合、缓存或读模型
  • 强一致降级为最终一致

那个触发器很典型：它原来负责在插入成员时自动填 room_name。拆库之后它跨了两个服务的数据，只能删掉，改由应用层写入。

触发器、外键、跨库 JOIN，本质上都是"假设大家在一个库里"的产物。拆库就是把这类假设一条条找出来。

另外两个和数据边界直接相关的改动：

message.id 改为非自增。 消息的主键由 ws-service 用 Snowflake 生成，不再依赖数据库自增。这样消息在落库之前就已经有全局唯一 ID，可以安全地做重试、幂等和跨实例排序。

增加 client_msg_id 和 (sender_id, client_msg_id) 唯一索引。 客户端断线重发时，同一条消息可能被投递多次。Kafka 只能保证至少一次，所以消费端必须能识别重复。唯一索引是最后一道兜底。

迁移完成后用合成数据验证：5 张业务表数据条数全部 1/1，跨库外键 0 个，触发器 0 个。

数字比"我觉得应该没问题"可靠。

四、Nacos 是地址簿，不是调用者

服务拆开之后，第一个问题就是：A 怎么找到 B？

我用了三种通信方式，各管一件事：

场景 方案 特点
同步查询 OpenFeign + LoadBalancer + Nacos 实时、有返回值、会失败
异步可靠处理 Kafka 持久化、可重放、至少一次
实时广播 Redis Pub/Sub 低延迟、不持久、发完即忘

这里最容易混淆的是 Nacos 和 Feign 的分工：

Nacos 是地址簿，负责"B 现在在哪几个 IP 上"；Feign 是打电话的人，负责"发起这次调用"。

Nacos 不知道你要调什么接口，也不替你重试。它只解决服务发现。

另一个常被问的问题是：Kafka 和 Redis Pub/Sub 能不能互换？

不能，因为它们保证的东西不一样。

  • Kafka 把消息写盘，消费者可以按 offset 重放。消息必须先可靠落库，再谈推送。
  • Redis Pub/Sub 不存消息，订阅者掉线就错过。它只适合"现在在线的人，立刻收到"。

所以消息链路是：

Kafka 负责"不能丢"，Redis Pub/Sub 负责"足够快"。把两件事交给一个组件，最后一定有一头不达标。

还有一条底线：不共享数据库表。 共享表看起来最省事，实际上是把两个服务的发布节奏重新绑死，等于白拆。

五、网关只做入口该做的事

网关不是业务服务。它不查用户、不拼消息，只做入口该做的事：

  • 统一入口和路由
  • JWT 鉴权
  • 清洗客户端伪造的身份头
  • 注入可信的 X-User-Id
  • CORS
  • 后续的登录限流

路由按业务域划分：

JwtGlobalFilter 里有一个动作容易被忽略，但它是整个信任模型的根：

删除客户端传来的 X-User-Id 和 X-Internal-Token，只注入网关自己解析出来的值。

如果不删，客户端可以随便带一个 X-User-Id: 1，下游服务又信任这个头，等于任何人可以直接冒充管理员。

信任链必须只有一个入口：客户端 → 网关 → 下游。下游不再解析 JWT，只信任网关注入的身份。

运行时验证最能说明问题：

  • Nacos 注册成功
  • 健康检查 UP
  • 不带 Token 请求 → 401
  • 带合法 Token 请求 → 因为 user-service 还没启动，返回 503

503 不是失败，反而是证据：鉴权已经通过，路由也已经生效，只差下游服务。 如果返回的是 401，说明 token 没过；如果返回 404，说明路由没匹配上。错误码本身就是链路的路标。

六、跨服务契约先统一命名

拆服务之前，原项目把跨服务传输的对象也叫 VO。拆开之后这套命名会直接制造混乱。

我统一成四类：

后缀 用途 放在哪
DTO 服务之间传输的数据 muchat-api
VO 返回给前端的展示对象 各服务内部
DO 数据库持久化对象 各服务内部
Event Kafka / Redis 异步事件 muchat-api

规则很简单：DTO 是跨服务契约，VO 是前端视图，DO 是数据库形状，Event 是异步消息。 四者混用，最后一定会出现"这个字段到底该不该给前端"的争论。

今天踩的坑

  1. Maven 下载失败。 Maven Central 和阿里云镜像都出现 TLS handshake 失败，配置镜像并固定 TLS 1.2 后恢复。
  2. Windows 提交内存耗尽。 Maven 测试 JVM 连 128MB 都申请不到，原因是 Docker/WSL、IDE、浏览器一起占满了 commit。处理办法是停掉不用的容器、降低测试堆，并给 WSL 加内存上限。
  3. 8080 被占用。 占用者是 Windows 的 svchost.exe。没有去动系统服务，网关改用 9080。
  4. Nacos 创建 namespace 返回 false。 不是失败，是它已经存在。用 GET 接口确认 muchat-dev 在，就够了。
  5. VO/DTO 命名混淆。 原项目把跨服务对象也叫 VO，迁移时统一改成 DTO。

前四个坑有一个共同点：报错信息指向的地方，往往不是问题所在。 TLS 失败看起来像网络，实际是协议版本；memory 失败看起来像代码，实际是整机资源；namespace 返回 false 看起来像创建失败，实际是幂等。

今天最值钱的三条

  1. 拆服务的单位是业务域，不是数据库表。 先问"谁负责写、谁负责改、谁负责扛量"，再决定表怎么放。
  2. 拆库的核心是删除"大家在一个库里"的假设。 跨库外键、触发器、JOIN，一条条找出来，换成软引用、API 组合和最终一致。
  3. 信任链只能有一个入口。 网关校验 JWT、清洗身份头、注入可信用户 ID；下游无条件信任网关。少一步，就是越权漏洞。

留给自己的六个问题

  1. 为什么 users 和 user_contacts 不拆成两个服务？
  2. 为什么 message 要独立成服务？
  3. 删除外键后，如何保证消息的 sender_id 仍然有意义？
  4. 网关为什么要删除客户端传来的 X-User-Id？
  5. 为什么 Nacos 不能替代 Feign？
  6. Kafka 和 Redis Pub/Sub 各自负责什么，为什么不能互换？

下一步

Task 5：抽取 user-service。

重点是把账号、资料、联系人接口迁出去，注册到 Nacos，并且把验证码从本地 HttpSession 改成 Spring Session + Redis——服务多实例之后，本地 session 就不再是"会话"，而是"某个实例碰巧记得你"。

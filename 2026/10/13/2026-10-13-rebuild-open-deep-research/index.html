5700 行里只有 1060 行值得学：我如何拆解 open_deep_research

学习日期：2026年10月13日
项目：deepsearch（从零重建 open_deep_research）
环境：Python 3.11 / LangGraph 1.x

写在前面

我给自己定了一个学习项目：从零重建 langchain-ai/open_deep_research。不是为了抄一遍，而是为了把 LangGraph 学透，顺便做出一个能讲的作品。

第一天做的第一件事不是读代码，而是算这个仓库到底有多少行值得学。

一、先算教学核心

整个仓库 5700 行，一开始我以为要全读懂。拆开之后发现：

文件 行数 性质
deep_researcher.py 718 核心——整张图
state.py 95 核心——状态设计
configuration.py 251 要学
utils.py 925 约 700 行是集成胶水（20 个搜索引擎适配、MCP 接入、Tavily 客户端）
prompts.py 367 提示词文本，不是逻辑

真正的教学核心约 1060 行。

这不是说胶水不重要，而是说：读开源项目时，先分清“教你概念”和“教你接某个服务”。utils.py 教你的是“怎么接 Tavily”，不是“怎么搭 agent”。

二、作者删掉了什么

读老版本时，我发现一个反复出现的模式：凡是可以用更强的模型或更好的服务直接解决的环节，作者都删掉了自己搭的脚手架。

问题 老版本 现版本
网页抓不下来 自己写爬虫（requests + BeautifulSoup） 外包给 Tavily
搜回的内容太多 自己搭 RAG（分块 + 向量 + 检索） 交给 LLM 摘要
怎么保证不跑飞 计划-执行 + 人工审批 让模型拿工具自己跑

作者为此写过一篇 “bitter lesson” 博客。这个取舍比代码本身值钱：不是“RAG 过时了”，而是当模型能力足够时，很多中间层可以删掉。

三、协议兼容 ≠ 能力兼容

我本来打算做一个“模型接入层”，兼容 OpenAI / Anthropic 两家协议。后来发现两件事：

  1. 兼容层根本不存在。 上游只有一行 init_chat_model(configurable_fields=("model", "max_tokens", "api_key"))。支持 20 个 provider 的是这个函数，不是我。
  2. 协议通 ≠ 能跑。 /v1/chat/completions 只规定“怎么收发”，不保证高级字段都在。很多“兼容 OpenAI 协议”的厂商，tool calling 是残的：有的不支持，有的流式格式错乱，有的不支持并行调用。

失败方式特别阴险：不报错，但也不干活。 模型收到工具定义不调，直接编一个答案给你。

所以第一步不是写抽象层，而是验证：这个端点到底能不能正常返回 tool_calls。这是 agent 项目的生死线。

四、v0.1 / v0.2 跑通后发现的三个坑

1. 工具描述是提示词，不是注释

@tool 会把函数名、docstring、类型标注变成模型看到的工具定义：

你写的 模型看到的
函数名 search "name"
docstring "description"
类型标注 query: str "parameters" 的 JSON Schema

所以 docstring 该写“什么时候用”，而不是“这函数干什么”。

上游 think_tool 的 docstring 写的是 “When to use: - After receiving search results…”，那不是文档，是给模型的行为指令。

2. 「研究完成」不等于「有答案」

加了 ResearchComplete 工具后，循环能自己收手了，但最终回答是空的。因为：

  • ResearchComplete 的参数是 {}，它没有地方装答案
  • 它是“我搜够了”的信号，不是交付物

「研究完成」和「写出报告」是两件事，需要两次独立的模型调用。 上游正是这么做的：主管节点收集 notes，交给独立的 final_report_generation 节点写报告。

判断标准：参数是“指令”（短、结构化）→ 工具；参数是“交付物”（长、给用户看）→ 节点。

3. 从循环切到产出，必须清理上下文

写报告节点一度把工具调用语法（DSML）漏进了正文。原因是上下文污染：它拿到的是全部历史，里面全是“怎么调工具”的示范，模型有很强的模仿本能。

修法：

  1. 用 get_buffer_string() 把历史拍平成纯文本再喂
  2. 提示词里明确禁止调用工具

上游天然避开这个：final_report_generation 拿到的是 "\n".join(notes)——纯字符串，不是消息历史。

凡是“从循环切到产出”的那一步，都要做上下文清理。

五、最贵的一条：看懂 ≠ 验证过

同一天里，至少有三个坑是看懂代码也看不见的，只有跑起来才暴露：

  1. Windows 终端中文乱码（PYTHONIOENCODING=utf-8 才能修）
  2. load_dotenv() 在 REPL / stdin 里会崩（它靠调用栈找 .env 文件）
  3. 推理模型的 reasoning_content 会不会污染正文（只能实测）

“看懂”给的是“我会了”的感觉，但它不改变任何一个坑的存在。

还有一个反复出现的模式：架构讨论五轮，代码零行。 从“模型接入层”到“协议兼容层”，五次都在为“以后可能要什么”做设计，而全部发生在跑通 v0.1 之前。

抽象要在有第二个用例之后再抽，不能提前。

下一步

v0.1 和 v0.2 跑通后，下一步是 v0.3：supervisor 拆题 + 并行 researcher。

三个研究员同时跑的话十几秒，排队的话四十秒。时长会说话。

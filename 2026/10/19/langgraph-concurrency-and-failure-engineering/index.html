别把 max_concurrency 当成研究员并发数：LangGraph 并发与失败工程笔记

学习日期：2026年10月19日
项目：deepsearch（从零重建 open_deep_research）
环境：LangGraph 1.2.15 / Python 3.11

写在前面

前一阵子把 open_deep_research 的核心架构从零重建了一遍：StateGraph、ReAct 循环、supervisor 拆题、并行研究员、配置系统、checkpointer 与 interrupt。能跑通之后，我开始做第二阶段——加深。

重建阶段解决的是“能不能跑”；加深阶段解决的是三个更接近生产的问题：

  1. 同时跑几个？谁在控制？
  2. 失败了怎么办？重试、超时、降级怎么配合？
  3. 怎么知道一次运行里到底发生了什么？

这篇文章记录其中最容易讲错的三个点，以及一个藏得很深的静默 bug。

一、max_concurrency 不是“研究员并发数”

我一开始以为，给图传 max_concurrency=2，就是“最多两个研究员同时跑”。

实测之后发现：它是整张图一次运行的全局信号量，主管、研究员、压缩、汇总全都走这个闸门。

实验

用一个不调用模型的图：6 个任务，每个 sleep(0.5)。

结果：

配置 峰值并发 总耗时
max_concurrency=1 1 3.05s
max_concurrency=2 2 1.52s
max_concurrency=3 3 1.02s
不设 6 0.51s
asyncio.gather 不设信号量 6 0.51s
asyncio.gather + Semaphore(2) 2 1.52s

源码里是什么

异步执行器给每个任务套了一个 asyncio.Semaphore：

同步路径则把它当成线程池的 max_workers。

所以：

  • Send 只负责派发，不负责限流
  • asyncio.gather 本身也不限流，要自己加 Semaphore
  • max_concurrency 限制的是整张图同时在跑的任务数

和上游的 max_concurrent_research_units 不是一回事

上游 open_deep_research 里还有一个 max_concurrent_research_units。它做的事完全不同：

它直接切掉多余的 tool call，超出的返回一条错误 ToolMessage。它限制的是“一次允许派出多少个研究分支”，是扇出宽度，不是运行时并发。

机制 限制什么 超出时
max_concurrency 整张图同时在跑的任务数 排队
gather + Semaphore 某个阶段同时跑的任务数 排队
max_concurrent_research_units 一次允许派出的研究分支数 直接拒绝

这三个概念混在一起，面试时很容易露馅。

二、重试会占着并发名额

节点级重试用 RetryPolicy：

它重试的是整个节点函数，不是某一行。

这带来三个后果。

1. 重试期间仍占并发名额

LangGraph 把整个 arun_with_retry 提交给执行器，而执行器在任务外面套了信号量。所以节点在退避等待时，名额不释放。

max_concurrency=2，两个节点都在重试等待，第三个节点只能排队。

2. 副作用必须幂等

如果节点里先写数据库、再调模型，模型超时后节点重试，数据库会被写两次。重试不是“免费的第二次机会”，它会重跑整个函数。

3. 客户端重试和节点重试会相乘

ChatAnthropic(max_retries=2) 自己会重试，外面再套 RetryPolicy(max_attempts=3)，最坏情况是 3 × 3 = 9 次调用。调参时要把两层乘起来算。

哪些异常会重试

LangGraph 的默认策略是：

  • ConnectionError、HTTP 5xx → 重试
  • ValueError、TypeError、LookupError 等 → 不重试

别自己写一个 except Exception: retry，那会把永久失败（比如 400 参数错）也重试一遍，纯烧钱。

三、error_handler 返回 dict，分支就结束了

节点重试耗尽后，可以交给 error_handler 兜底：

NodeError 会被自动注入，里面有 error.node 和 error.error。

这里有一个非常反直觉的细节：如果返回普通 dict，分支就到此结束了，下游节点不会执行。

我实测过：失败节点后面明明有一条边指向 after，但 handler 返回 dict 时，after 根本不会跑。

四、timeout 只对异步节点有效

给节点加超时：

两个前提：

  1. 节点必须是 async def
  2. 外层必须用 await app.ainvoke(...)

同步节点会直接报：

原因是同步函数一旦开始执行，Python 没法安全地从外面掐断；异步函数在 await 处会把控制权交出来，框架才有机会取消它。

超时后抛 NodeTimeoutError，error_handler 可以在 error.error 里拿到它。

还有一个坑：NodeTimeoutError 不在默认的“不重试”名单里。如果你同时给节点配了 RetryPolicy，超时会先被重试到 max_attempts，才进兜底。想让它直接进兜底，就把 retry_on 写清楚。

这个 bug 最值得记住的地方是：它不报错。图正常结束，日志正常打印，只有最终报告是空的。静默失败比直接崩溃更难发现。

六、用 astream_events 看清一次运行

print 只能告诉你“我打印了什么”；trace 能告诉你“谁调了谁、各花了多久”。

LangGraph 的 astream_events 会吐出结构化事件，每个事件带 run_id 和 parent_ids，可以还原成一棵调用树：

实际输出大概是这样：

有了这棵树，你就能直接回答：

  • 哪个节点最慢？
  • 每个研究员调了几次模型？
  • 工具有没有失败？
  • token 花在哪个阶段？
  • 子图的出口有没有走到？

trace 不是“更花哨的日志”，它是带父子关系、耗时和 token 的结构化数据。打印只是它的一种展示方式。

最后的三个结论

  1. max_concurrency 是整张图的全局信号量，不是研究员并发数；max_concurrent_research_units 是扇出宽度上限，两者不是一回事。
  2. 重试会占着并发名额，退避等待时也不释放；重试还会重跑整个节点，副作用必须幂等。
  3. error_handler 返回 dict 只更新状态、分支结束；要接着走必须 Command(goto=...)。

如果只让我留一句，我会留这个：

失败处理的目标不是“让图不崩”，而是“失败可见，并且有一个可预期的出口”。

图活着但报告是空的，和没处理失败差不多。

下一步

  • 跑 3 次基线，记录总耗时和各阶段耗时，取中位数
  • 做一个小型评估集：5 个固定问题 + 必含要点 + 规则检查 / LLM judge
  • 把假的搜索工具换成真实搜索，并用评估集证明它确实变好了

重建是“能不能跑”，加深是“跑得稳不稳、贵不贵、怎么证明它好”。这条路还长，但至少现在，失败不再静默了。
